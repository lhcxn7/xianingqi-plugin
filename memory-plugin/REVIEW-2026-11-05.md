## 问题清单

### 致命

无。插件的主链路（自有 log.jsonl 记录 → 跨会话关键词召回 → 注入）在今天的直接 API 实测中已通（s1 立约冰镇酸梅汤，s2 新进程召回首位命中 score 15.00）。

### 重要

#### 1. MEMORY.md 解析器与 skill v2.4 的真实格式不匹配，layer 2 / 归档 / layer 1 喜好基本读不到

- 证据文件：`core/src/memory-file.ts:29`（`DATE_HEADING` 只认 `### YYYY/MM/DD`）、`:30-31`（`ENTRY_LINE` 要求 `- HH:MM [...]` 开头）、`:92,95`（layer 1 只认 `喜欢` / `不喜欢`）、`:164-165`（章节切换只认含 `最近|30天` / `归档|月度` 的标题）。
- skill v2.4 实际写的格式（`skills/xia-ningqi/SKILL.md`）：
  - `:142`：日期标题是 `## 2026/11/02`（二级标题，不是 `###`）；条目是 `[14:32] 事件一句话`（方括号时间开头，无前导 `- `，无 role/window/importance 元数据）。
  - `:141`：layer 1 用词是 `喜好` / `厌恶`，不是 `喜欢` / `不喜欢`。
  - `:143`：第三层叫“旧月份总结区”，既不含 `归档` 也不含 `月度`，且总结行格式未在 skill 里定死。
- 实证：按 skill v2.4 逐字写的 MEMORY.md + `MEMORY-2026-10.md` 喂给 `parseMemoryText` / `parseArchiveText`，结果 **layer2 = 0 条、layer3 = 0 个月、likes = []、dislikes = []、归档 = 0 条**（仅 `名字` / `阶段` / `约定` 因键名巧合读到了；`喜好` / `厌恶` / `最后更新时间` 全进了 `extra`，而 `formatLayer1` 不输出 `extra`，所以 `memory_search` 的 layer1 显示也会丢喜好）。
- 影响：插件自称“读全部三层 + 月度归档”、README 称“格式兼容现有 xia-ningqi-data”，对真实 skill 写出的文件基本失效。主链路不受影响（召回主力是插件自写的 log.jsonl，实测已通），但“旧记忆可召回”这条能力是断的；且 `core/test/demo.ts` 的 fixture 是插件自定格式却标称“skill-shaped”，测试名具有误导性，没有任何一个测试用过 skill 的真实格式。
- 修复方向（二选一，需用户定）：改解析器去兼容 `##` 日期标题 + `[HH:MM]` 条目 + `喜好/厌恶` 键（推荐，skill 是 canonical）；或改 skill 统一写解析器认的格式（会动已发布的 v2.4，不推荐）。

#### 2. `restoreSnapshot` 会删掉目标快照里没有的非托管文件，包括日记；删除-复制序列本身不抗崩溃

- 证据：`core/src/snapshot.ts:83-92`：`restoreSnapshot` 先拍安全快照，然后 `readdirSync(dataDir)` 删掉除 `.snapshots` / `.tmp-` 外的**全部**文件，再从目标快照拷回来。
- 日记文件就放在同一个 `xia-ningqi-data` 文件夹里（skill v2.4 `:150`）。如果目标快照早于日记创建，恢复会把当前日记删掉；安全快照（`pre-restore-*`）里虽有副本，但要用户自己去 `.snapshots` 里翻。
- 同一问题：崩溃发生在删完、拷回之前，数据目录是半空的（只剩安全快照兜底）。
- 另外 `pruneSnapshots`（`:53-59`）按 keep=30 删旧快照——快照是副本，记忆本身还在 log 里，风险低，但与“永不删除”的说法冲突（见小毛病 a）。

#### 3. DSH 壳子的真实事件信封形状未经验证，`source.kind` 过滤存在静默失效模式

- 证据：`dsh-plugin/src/index.ts:246`，`session/event` 的 `user/message` 分支要求 `eventSourceKind(event) === "user"`，否则直接 return；`eventSessionId`（`:~95`）在信封缺 `sessionId` / `session.id` / `agentId` 时回退到 `"default"`。
- 风险：如果真实 DSH 的 user/message 事件不带 `source.kind === "user"`，**全程一条都不记，且不报错**——静默失效。mock 测试用的是插件自己假设的信封形状（`mock-test.ts` 的 `emit` 直接按插件的假设喂数据），测不出这个问题；今天的直接 API harness 只模拟了 core，不覆盖 DSH 事件。
- 同理：若信封缺 session id，所有会话共用一个 `SessionState`，一个会话触发 persona 后，别的任务会话也会被当成人设会话记录（跨会话污染）。
- 这是目前壳子部分最大的未验证点，需在用户自己电脑的真实 DSH 里用一次真实对话验证（检查 log.jsonl 是否增长、以及 task 会话是否被误记）。

#### 4. 无关键词命中时仍注入最近 10 条，且 pre-step 的注入不分人设/任务窗口

- 证据：`core/src/recall.ts:78-90`，无命中时回退为“最近的、heavy 优先”，score 0，仍返回 up to `limit` 条；`dsh-plugin/src/index.ts:202-222`，pre-step 对**所有**窗口的用户消息都跑 `core.recall` 并在 turn 1 append 到 `decision.messages`，没有任何 `session.persona` 判断。
- 实证：空库里只有两条无关记录时，`core.recall("帮我写个脚本")` 仍返回 2 条命中并生成可注入文本（`/tmp/recall-fallback.mjs`）。按壳子逻辑，任务窗口的一句“帮我写个脚本”会在 turn 1 被追加人设记忆；人设窗口里任何一句不相关的话也会注入最近历史。
- 后果：每轮白白烧 token（默认上限 1500）；模型可能把无关的最近记忆当成相关上下文。注：skill 的任务窗口本来就要求开场读记忆（layer 1 + 最近 30 天），所以“任务窗口也注入”不一定算违规，但与插件自述“只注入 skill 没读到的内容”有张力（回退注入的是原始片段，skill 的 layer 2 摘要里可能已有同一件事），且记录侧是 persona 门控、注入侧不是，这种不对称在 README 的 persona/task 一节里没写明。

#### 5. `memory_remember` 工具没有人设窗口门控

- 证据：`dsh-plugin/src/index.ts` 的 `memory_remember.execute` 直接 `core.record({ window: "persona", importance: 默认为 heavy, sessionId: "manual" })`，不检查调用会话是不是人设会话，且以 `role: "user"` 记录模型传来的任意文本。
- 风险：任务窗口的模型只要主动调这个工具，就能把任务内容写进人设记忆——把 v1.6“任务窗口不写记忆”规则在插件自己的写路径上重新撕开一道口子。发生概率低（模型须主动调用），但属于已知的防污染规则被绕过。另：描述里未限定窗口，模型在任务窗口调用它并不算“违规操作”，全靠模型自觉。

### 小毛病

- **a. “永不删除”说法失实**：根 README、core README、`core/src/core.ts` 头注释都写“never deletes anything / Nothing is ever deleted”，但 `pruneSnapshots` 删旧快照、`restoreSnapshot` 删数据目录文件（见重要 2）。应改成“永不删记忆条目，快照按 keep=30 轮换，恢复会替换数据目录文件”。
- **b. `estimatedTokens` 文档与实现不一致**：`core/src/types.ts:85` 注释写“layer 1 + hits”，`core/src/recall.ts:106` 实际只计 hits（layer 1 本就不注入）。数字本身没错，注释错。
- **c. rollover 截断非原子**：`core/src/core.ts:231` 用 `writeFileSync(log, "")` 直接清空；若崩溃发生在分段写完、清空之前，条目会同时存在于 log 和分段里，重载后重复（同 id，recall 的 byId 会去重，但 `stats().totalEntries` 会虚高）。
- **d. 去重发生在 token cap 之后**：`core/src/core.ts` 的 `recall()` 先由 `recallFromEntries` 按 cap 截断、再按原文去重；原始片段与其归档副本可能占掉两个 cap 名额，去重后实际返回条数少于 cap 允许值。
- **e. log 追加不 fsync**：`core/src/log.ts:17` 的 `appendFileSync` 无 fsync；进程崩溃无碍，断电会丢尾部。索引只在 flush 时落盘，进程崩溃后靠 logBytes 失配重建（能兜住）。
- **f. 索引过期判断只看总字节数**：`core/src/keyword-index.ts:load` 只校验 `version` + `logBytes`；用户手改 log.jsonl 且字节数恰好不变时会读到过期索引。对插件自己的写模式够用，手改场景下脆弱。
- **g. 快照无完成标记**：`core/src/snapshot.ts:takeSnapshot` 拷一半崩溃会留下一个不完整快照目录，`listSnapshots` 会收录它，`restore` 可能用它。
- **h. `parseEntryLine` 的 id 用弱哈希**：`core/src/memory-file.ts:50-58` 的 31 位哈希 + 同日期同分钟同文本即同 id；不同文本同分钟碰撞概率极低，可忽略；相同行同分钟会被 recall 的 byId 去重。
- **i. turn 计数按 pre-step 调用次数**：`dsh-plugin/src/index.ts:202`，无用户文本的 pre-step 也消耗 turn 1 的 append 名额；第一次 pre-step 若无文本，真正的 turn 1 将只走 `systemPrompt.context`（按研究报告，turn 1 可能收不到）。
- **j. recall context 的 disposer 是全局单变量**：`dsh-plugin/src/index.ts` 的 `disposeRecallContext` 跨会话共享；多会话交错时会互相释放对方的动态 context。实际使用中一次一个会话，影响小。
- **k. 工具注册失败静默吞掉**：`dsh-plugin/src/index.ts` 末尾 `.catch(() => {})` 无任何日志；DSH 里 `@deepseek-ai/dsh-tools` 加载失败时两个 fallback 工具悄悄缺席，难排查。
- **l. 分词范围小缺口**：`core/src/tokenize.ts` 的 CJK 段不含扩展 B 区（`\u20000+`）和假名；纯中文场景可忽略。
- **m. `record()` 每次全量重读 + 全量排序**：`core/src/core.ts:record` 每记一条就 `currentLogEntries()` 读一遍文件、`this.entries.sort` 排一遍；1000 条以内无感，量大了才有意义。
- **n. pre-step 每次重读 MEMORY.md + 全量扫归档**：`dsh-plugin/src/index.ts:208` 经 `readLayer1` 每次都 `load()` 全文；量小无感。
- **o. 测试缺口**（均未覆盖）：索引过期重建、快照轮换（keep=30）、二次 rollover 合并已有分段、无命中回退行为、原文去重、空查询、会话重建后 persona 重置、`source.kind` 缺失、diary 在恢复中的命运、双进程同目录写（无文件锁，单写者假设未在文档里写明）。

## 结论

插件主链路没问题，测试全绿，安全与干净项全部通过。但有两个重要问题值得先修再推：
1）解析器读不到 skill v2.4 真实格式的 MEMORY.md/归档（重要 1）——旧记忆召回基本是断的；
2）恢复会删目标快照里没有的日记等文件（重要 2）——一次手滑恢复就可能丢日记（安全快照可救，但要手动翻）。
其余重要项（3、4、5）是“真实 DSH 未验证 + 门控缺口”，建议在用户电脑的真实 DSH 里验过 3 之后再定是否发版。
