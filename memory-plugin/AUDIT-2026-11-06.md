# 记忆插件全面审计 — 2026-11-06 凌晨

审计对象：`memory-plugin/` 0.1.2（core + dsh-plugin）。只读审计，**没有改插件源码**。
准绳：真实 DSH 0.2.1-rc.5 源码（`<npx 缓存>/node_modules/@deepseek-ai/`），插件代码怎么写的不算数。
验证手段（VM 上，测试数据只用 `<测试工作区>/`，没碰用户真实数据，没读真 key）：
- 通读插件全部源码（core + shell）。
- 3 次 live headless 运行（假 key，只过门禁，轮次在模型调用处 401 失败是预期的）：
  - Run A：envelope dump（pre-step decision 字段、agent/created、全部 session/event 类型+data 键）。
  - Run B：tools 探针（`ctx.tools.get` / `schemas()`）+ 3 条 user/message 事件的 id/source 对照。
  - Run C：碰撞测试——diag 插件先占 `memory-plugin:recall` 这个名字，模拟第二个会话的 context 还活着。
- pnpm link: 安装测试（`/tmp/pnpm-link-test`，`pnpm install` 后看 lockfile 和 node_modules）。
- Node 毒化测试（`/tmp/poison-test`）：`memory_remember` 传 undefined/number 文本会发生什么。

结论先说：**2 个 blocker，7 个 major，约 15 个 minor。**最要命的两个都是“平时好好的，一触发就全炸，而且炸完很难恢复”的类型。

## BLOCKER

### B1. 多会话 systemPrompt.context 名字冲突——第二个窗口的人设轮次必炸

**插件位置：** `dsh-plugin/src/index.ts:275-291`（`refreshRecallContext`，`context()` 调用没有任何 try/catch）；同文件 `:296-299`（`agent/created` 重置状态时直接丢掉旧 disposer，不先 dispose）；`:266`（静态 section 同样注册在全局层）。

**DSH 证据：**
- `dsh-scope/lib/index.js:312-314`：`scopeOf(ctx)` 只读 `ctx[kScope]`，插件 ctx 没有 scope tag → `undefined`。
- `dsh-scope/lib/index.js:189`（`ScopedLayers.effect`）：scope 是 `undefined` 时注册进 **全局层**。
- `dsh-system-prompt/lib/index.js:203-205`：同一层里同名 context 再注册就抛错，报错信息原文就是修法提示：`prompt context "…" is already registered (for a per-agent override, register through that agent's agent.ctx instead)`。
- `dsh-system-prompt/lib/index.js:193-197`：`context()` 返回的是 Cordis effect disposer（函数），插件的 `typeof handle === "function"` 判断是对的。

**实测（Run C，live 复现）：** diag 插件先注册了 `memory-plugin:recall`，记忆插件 turn 1 step 0 直接炸：
`agent/error turn=1 step=0 — prompt context "memory-plugin:recall" is already registered (for a per-agent override, register through that agent's agent.ctx instead)`，轮次在模型调用前就失败。

**用户会看到什么：** 开两个窗口（或重开一个会话）后，第二个会话里只要一问到能命中回忆的话题，每一轮都报 `本轮运行失败 prompt context "memory-plugin:recall" is already registered`。没有命中时轮次正常，所以是时好时坏，更难查。第一个会话闲着不刷新，它的 context 永远占着名字，第二个会话永远注册不上——直到重启 DSH。同一个会话重建（`agent/created` 对同一 id 再触发）也会自己撞自己：旧 context 泄漏了，新状态的 disposer 是 null，根本 dispose 不掉。

**修法（按 DSH 自己的提示）：**
1. 动态 recall context 走 agent 作用域注册：`decision.agent.ctx.systemPrompt.context(...)`（pre-step 的 `decision.agent` 就是那个 agent，live 已证 `agent.id` 即会话 id），不要走插件全局 ctx。
2. `refreshRecallContext` 里的 `context()` 调用包 try/catch：注册失败只降级为“本轮不注入”，绝不能把轮次炸掉。
3. `agent/created` 重置状态前先调旧 disposer；再加一个会话结束/重建时的 dispose（没有现成 hook 的话，至少在重置时 dispose）。
4. 静态 section（`:266`）同样加防重：catch 住 duplicate 错误（两个 profile 同进程加载时会撞）。

### B2. 一条坏记录就能把插件永久毒死——`memory_remember` 无校验 + `record()` 先写盘后校验

**插件位置：** `dsh-plugin/src/index.ts:550`（`memory_remember` 的 execute 直接把 `args.text` 传给 `core.record`，不校验）；`core/src/core.ts:146`（先 `append` 写盘）→`:158`（再 `index.add` 才抛错）；`core/src/core.ts:86-93`（构造函数里 `ensureDir` 后 `index.build`）；`core/src/keyword-index.ts:77`（`tokenize(entry.text)`）；`core/src/tokenize.ts:17`（`text.toLowerCase()`）。

**DSH/触发链证据：** 触发器在 M2（工具是原始 DSL 注册的，模型看到的 schema 里根本没有 required 字段，模型很容易不带 `text` 调 `memory_remember`）。

**实测（Node，`/tmp/poison-test`，已复现）：**
- `record({text: undefined})`：`log.jsonl` 里先写入一条**没有 `text` 字段**的行（`JSON.stringify` 会丢掉 undefined 字段），然后在 `index.add` 抛 `Cannot read properties of undefined (reading 'toLowerCase')`。
- `record({text: 123})`：同样先写盘（`"text":123`），再抛 `text.toLowerCase is not a function`。
- 之后**全新 `new MemoryCore`**（等于重启 DSH）：构造函数 `index.build` 在毒行上抛错 → `apply()` 抛错 → 插件整个加载失败。
- 即使 index.json 恰好是新的（构造函数侥幸过去），之后每一次 `recall()` 都在 `tokenize(e.text)` 上抛错 → 每个人设轮次都在 pre-step 炸掉。

**用户会看到什么：** 某天模型调了一次没带文本的 `memory_remember`（用户完全看不到），之后重启 DSH，插件悄悄没了（只有 DSH 日志里一行 fiber 报错）；或者每个人设轮次都报 `toLowerCase` 错。恢复办法只有手工去 `log.jsonl` 里删掉那行坏记录——需要手工处理。

**修法（三层都要）：**
1. `record()` 入口校验：`text` 不是非空字符串就拒绝（抛错在 append **之前**），`memory_remember` 的 execute 也先校验 `args.text`。
2. 防御性：`tokenize()` 对非字符串返回 `[]`；`AppendLog.readAll()` 丢弃没有字符串 `text` 的行；`recallFromEntries` 跳过 `text` 非字符串的条目。坏行永远不该让构造函数和 recall 炸掉。
3. 根治触发器：修 M2（让 `defineTool` 真正生效，参数校验挡住坏调用）。

## MAJOR

### M1. 全局 recall context 泄漏进任务窗口——“任务窗口不注入”是假的

**插件位置：** 同 B1（`index.ts:275-291` 全局层注册）。

**DSH 证据：** `dsh-scope/lib/index.js:177`（`ScopedLayers.merge`）：任何 scope 的有效视图都从全局层开始合并。插件的 recall context 在全局层，所以**所有**会话（包括任务窗口）的 prompt 组装都会把它包含进去。

**用户会看到什么：** 人设窗口聊完开个任务窗口干活，任务窗口的 prompt 里混着上个人设会话的回忆片段；闲置人设会话的旧 context 也会一直污染之后开的任务窗口，直到那个人设会话再刷新一次。插件注释说“任务窗口不注入”，只在 pre-step 路径上成立，prompt 组装层面是假的。

**修法：** 同 B1——recall context 走 agent 作用域（`agent.ctx`），任务窗口自然看不到；静态 directives section 可以留在全局（它是通用文本，不是记忆）。

### M2. `defineTool` 在 link: 安装里永远解析失败，两个工具是“裸 DSL”注册的

**插件位置：** `dsh-plugin/src/define-tool.ts:14-18`（import 失败就静默 fallback 成 `(tool) => tool`）；`dsh-plugin/src/index.ts:447-499`（注册）。

**DSH/实测证据：**
- Run A/B live：diag 插件里 `await import("@deepseek-ai/dsh-tools")` 报 `ERR_MODULE_NOT_FOUND`；记忆插件的 `loadDefineTool` 走同一条解析路径，同样失败。
- Run B tools 探针 live：`memory_search=REGISTERED`，但 `parameters` 是原始 spec map（`{"query":{"type":"string","required":true,…},"limit":{…}}`，不是编译后的 JSON Schema），`execute` 是原始 `async (args) => { const result = core.recall(args.query, …`（没有 defineTool 的参数校验和 exec 透传）；`ctx.tools.schemas()`（`dsh-tools/lib/index.js:3119`，DSH 自己的“模型可见 schema”投影）原样返回这个 map——模型看到的工具 schema 就是坏的。
- pnpm 实测（`/tmp/pnpm-link-test`）：`pnpm install` 后 lockfile 里只有 link: 本身，**没有安装 `@deepseek-ai/dsh-tools`**，`node_modules` 里也没有；Node 按真实路径解析（symlink 会 realpath），profile 的 node_modules 不在解析链上。所以不论哪台机器，只要是 link: 安装，这个 import 就不可能成功。`define-tool.ts` 注释里“DSH 安装插件时会装上它”是错的。
- `dsh-tools/lib/index.js:2974-2982`（`register`）：只校验 `output.schema`/`render`，不校验 `parameters`——所以裸对象注册时不抛错，静默通过，坏在模型侧。

**用户会看到什么：** `memory_search` / `memory_remember` 基本不可用——模型看到的 schema 没有 `type: "object"`、没有 `properties`、没有 required，等于一个无参数的工具；模型要么永远不调，要么乱传参数；乱传就触发 B2 的毒化。`register` 不报错，所以这个问题在任何日志里都不显形。

**修法：**
1. 把 `@deepseek-ai/dsh-tools` 真正打进插件包：vendor 一份（或 build 时用 `prepare` 编译出 `index.js` + `lib/`，把编译好的工具定义随包发布），不要依赖运行时的裸 import。
2. `loadDefineTool` 的 fallback 失败时 `console.warn` 大声报警，不要静默 pass-through；注册后自检一次 `ctx.tools.get("memory_search").parameters` 是不是合法 JSON Schema。
3. 即使 defineTool 生效，插件的 execute 也要接第二个参数 `exec`（见 M4）。

### M3. `apply()` 里抛错 = 插件悄悄死亡，DSH 照常启动

**插件位置：** `dsh-plugin/src/index.ts:205`（`new MemoryCore`，无 try/catch）；`:266`（`section()` 注册，无防重）。

**DSH 证据：** `cordis/lib/index.js:1619`（`registry.plugin` 返回一个 fiber，不抛到调用方）；`cordis-plugin-loader/lib/index.js:453-463`（`_init` 里调 `registry.plugin`，不 await、不 catch）；`cordis/lib/index.js:975-982、1269、1312`（fiber 失败只记日志）。

**用户会看到什么：** dataDir 所在盘没了（盘符变了/磁盘被拔掉）、路径不可写、section 重名——DSH 正常打开，但记忆插件整个没加载，没有任何界面提示，只有日志里一行 fiber 报错。结合 B2，这就是毒化后“插件悄悄没了”的同一条路。

**修法：** `apply()` 顶层包 try/catch：`new MemoryCore` 失败就记一条清楚的错（写明 dataDir 和原因），并降级（比如用默认目录重试一次，或明确拒绝加载并在 UI 可见的地方报错）；`section()` 注册 catch duplicate。

### M4. `memory_remember` 的门控用的是“最近一次 pre-step 的会话”，不是调用者自己的会话

**插件位置：** `dsh-plugin/src/index.ts:222-224`（注释自己承认“DSH 不把调用会话传进 execute（未验证）”）、`:327`（`currentTurnSessionId = sid`）、`:~540`（门控读它）。

**DSH 证据（现已验证，注释过时了）：** `dsh-agent-loop/lib/index.js:511-518`：工具执行时 `exec: {callId, name, arguments, agent, signal}`；`dsh-tools/lib/index.js:3406`：`tool.execute(exec.arguments, exec)`——**第二个参数就是 exec，`exec.agent.session.id` 就是调用会话的精确 id**。

**用户会看到什么：** 单窗口时没事；两个窗口交错时，A 窗口（人设）的模型调 `memory_remember`，门控可能读到 B 窗口（任务）刚写下的 `currentTurnSessionId`——要么人设的合法写入被错拒，要么任务窗口的内容被错写进人设记忆（v1.6 的“任务窗口永不写记忆”规则就这么破了）。

**修法：** execute 签名改成 `(args, exec)`，门控用 `exec.agent.session.id` 查 `sessions` 表；`currentTurnSessionId` 只留作 exec 缺失时的 fallback。

### M5. 快照/会话结束从未真正跑过——“丢了能恢复”是空头支票

**插件位置：** `core/src/core.ts:293-300`（`endSession()`：snapshot + rollover + flush）；`dsh-plugin/src/index.ts` 全文——**没有任何地方调用 `endSession()` / `snapshot()` / `restore()` / `stats()` / `rebuildIndex()`**（grep 证实，只有定义和 `endSession` 内部自调）。

**用户会看到什么：** 文档承诺的防丢保护（定期快照、会话结束归档）实际上一次都没跑过；记忆文件损坏/误删时没有任何恢复点。`rollover` 只有 `record()` 满 1000 条时才触发（这条是活的），但 `snapshot()` 完全是死代码。

**修法：** 没有现成的“会话结束”hook（`agent/turn-stopping` 只在正常轮次结束时跑，`agent/created` 只有开始），所以：至少在 `compaction/start`（确实会触发）和 `ctx.effect` 卸载时调 `snapshot()`；或者加一个 `ctx.effect` 的定时器定期快照；再把 snapshot/restore 接到工具上（让模型/用户能主动触发），否则 `restore()` 永远调不到。

### M6. pre-step 里 `recall()` 抛错会炸掉整轮；`turn-stopping` 里 `flush()` 抛错也会炸掉整轮

**插件位置：** `dsh-plugin/src/index.ts:336`（`core.recall`，无 try/catch）；`:435-437`（`turn-stopping` 里 `core.flush()`，无 try/catch）。

**DSH 证据：** pre-step 是 waterfall，抛错直接向上传播（0.1.1 的 `decision.kind` 就是这么炸的）；`cordis/lib/index.js:289-294`（`serial` 里监听器抛错就中断并向上传播）；`dsh-agent-loop/lib/index.js:995-1010`（`turn-stopping` 在 turn 循环的 try 里，抛错进 catch → 轮次失败）。反过来，`session/event` 的监听器是被包住的（`dsh-session/lib/index.js:1231-1240`，只记 warn），所以 `:380/:411/:424` 的 `flush()`/`record()` 抛错不会炸轮次，只会悄悄丢一条记录——那是另一个小问题（见 minor）。

**用户会看到什么：** MEMORY.md 一时读不了、磁盘满了、dataDir 权限掉了——人设轮次直接报 `本轮运行失败`，而不是降级成“这次不注入”。`turn-stopping` 里 flush 失败更冤：她的话都生成完了，轮次却因为落盘失败被标成失败。

**修法：** pre-step 的 `recall()` 包 try/catch，出错记 warn、本轮不注入、继续走 `next()`；`turn-stopping` 的 `flush()` 同样包 try/catch；`session/event` 里的 `record()`/`flush()` 也包一层，记一条能看懂的 warn（现在是 DSH 内部 warn，用户看不到是哪条丢了）。

### M7. 会话重建后人设标记丢了——重开人设窗口，前半段聊天不进 log

**插件位置：** `dsh-plugin/src/index.ts:296-299`（`agent/created` 直接 `sessions.set(id, {persona:false, turns:0, disposer:null})`）。

**用户会看到什么：** 重开一个已有人设会话（agent 重建），插件忘了它是人设窗口；接着正常聊（不说触发词），双方的话全都不进 log，直到哪句又带上“夏柠柒”才恢复。log 里出现一段时间的空白，事后查才发现。

**修法：** 人设标记按会话 id 持久化（比如 core 里一个小文件，或启动时从该会话已提交的历史里扫一遍触发词）；至少不要在 `agent/created` 里无条件重置——已有状态先保留。

## MINOR

### m1. KeywordIndex 建了、存了，但一次都没被查过；recall 是全表线性扫描

**位置：** `core/src/keyword-index.ts:lookup`（grep 全仓无调用者）；`core/src/recall.ts:66`（每轮对每条 entry `tokenize(e.text)`）；`core/src/core.ts:flush`（每轮 turn-stopping 都把整个 index map 序列化写盘）。

**现象：** log 越长每轮越慢（O(n) 分词 + 全量 index.json 重写），而 index 本身是死代码。量小的时候感觉不到，聊上一年（上万条）就明显了。
**修法：** recall 改走 `lookup()`，或干脆不持久化这个不用的 index。

### m2. 去重按“文本一模一样”删——真重复的话会被误删

**位置：** `core/src/recall.ts` 去重段（key 是 `hit.entry.text.trim()`）。

**现象：** “好的”说了两次、同一个问题隔两天又问一遍，recall 结果里只剩一个，另一个的发生时间丢了。本意是去掉“log 片段 vs 归档副本”的重复，但连带把合法重复也删了。
**修法：** 去重 key 改成 `text + date` 或只对“log vs 归档”这对来源去重。

### m3. token 上限的切法：第一条再大也硬塞，塞不下就直接断掉不找小的

**位置：** `core/src/recall.ts` cap 循环（`if (hits.length > 0 && used + cost > tokenCap) break`）。

**现象：** 一条几千 token 的超长消息会独自冲破 1500 上限原样注入；排在它后面的、明明塞得下的小条目反而被丢掉。
**修法：** 超上限的条目跳过（continue）而不是 break；第一条也受上限约束（或截断）。

### m4. 单字中文查询查不到句子中间的字

**位置：** `core/src/tokenize.ts`（CJK 跑串只产 bigrams + ≤6 字的整串；单字 token 只有该字独立成串时才存在）。

**现象：** 问“汤”查不到“酸梅汤”那句（`梅汤` 这个 bigram 里没有单独的“汤”）；问“酸梅汤”没问题。单字查询基本失灵。
**修法：** 也产出单字 token（或在文档里写明单字查不到）。

### m5. 她的心声（reasoning 块）会被当成她说的话记下来

**位置：** `dsh-plugin/src/index.ts:messageText`（把所有带 `.text` 的 part 都拼起来，不分类型）。

**DSH 证据：** `dsh-llm/lib/index.js:1020-1040`（`BlockAssembler` 会把 `reasoning` 块组装进最终消息的 content 数组里）。

**现象：** 只有用带 reasoning 的模型时才触发——她的思考过程被记成对话原文，之后还可能被当成她说过的话重新注入。当前 `deepseek-chat` 一般不产 reasoning，所以是条件触发。
**修法：** `messageText` 跳过 `type === "reasoning"`（和 `tool-call` 一样）。

### m6. 纯图片/文件的消息记成空；图文混发只记文字，不留“有张图”的痕迹

**位置：** `dsh-plugin/src/index.ts:messageText` + `:398`（`if (!text) return`）。

**现象：** 只发一张图 → `""` → 不记录；图加一句话 → 只记那句话，log 里看不出当时发过图。
**修法：** 没有文本时记一个占位（如 `[图片]` / 附件名），让 log 至少知道这条存在。

### m7. 流式中断的半截话被当成完整的话记下来

**位置：** `dsh-plugin/src/index.ts:eventMessage`（只解 `data.message`，不看 `data.interrupted`）。

**现象：** 中断后结算的 `assistant/message` 只有半句话，插件原样记下，之后 recall 可能把半句话当成她说过一句完整的话注入。
**修法：** 读 `data.interrupted`，中断的要么跳过、要么在文本后标 `[未说完]`。

### m8. 归档里的她的话会被标成 `[user]`

**位置：** `core/src/memory-file.ts:parseEntryLine`（skill 格式 `[14:32] …` 没有角色字段，默认全是 `role: "user"`）。

**现象：** recall 注入块里，她的归档原话显示成 `[日期 时间 user] …`。只影响显示和去重，不影响命中。
**修法：** 归档命中在注入块里用中性标注，或让 skill 格式带上角色。

### m9. `decision.sessionId` 是死代码——真实 DSH 从不给它

**位置：** `dsh-plugin/src/index.ts:320-326`（优先读 `decision.sessionId`）；`dsh-plugin/src/types.ts:PreStepDecision.sessionId`。

**DSH 证据（live Run A/B）：** pre-step 收到的 decision 字段只有 `[messages, turn, step, signal, agent]`，`sessionId=undefined`；实际 sid 一直是 `resolveSessionId` 从 `ev.agent.id` 拿到的（live 证实 `agent.id` 就是会话 id）。

**现象：** 现在没事（fallback 能工作），只是误导——以后有人会以为 sessionId 是正路。
**修法：** 删掉这个优先分支（或注明 agent.id 才是真实来源）。

### m10. turn-1 追加的 recall 消息没有 id、content 是字符串，不符合 DSH 消息形状

**位置：** `dsh-plugin/src/index.ts:342-346`。

**DSH 证据（live Run B）：** 追加的消息在 session/event 里是 `data.id=undefined`、`content=string(len=655)`，而正常消息是 `content=array(1 text)` + 有 id（`createUserMessage` 会补 id）。

**现象：** 目前能正常提交和记录，没炸；但按 id 查、按序号排这类下游逻辑都可能跳过它，属于埋点。
**修法：** 追加时给它一个 UUID id，content 用 `[{type:"text", text}]` 数组。

### m11. `memory_search` 传了 undefined 的 query 就抛错（不是返回空结果）

**位置：** `core/src/core.ts:179`（`tokenize(query)`）；`core/src/tokenize.ts:17`。

**现象：** 模型乱调一次就拿到一个工具报错。是 M2 的子问题，修 M2（参数校验）就挡住了；同时 `recall()` 入口也该对非字符串 query 返回空结果。
**修法：** 同 B2 的防御层。

### m12. `endSession` / `snapshot` / `restore` / `stats` / `rebuildIndex` 在真实 DSH 里是死代码

**位置：** `core/src/core.ts:286-300` 等；shell 里零调用（grep 证实）。

**现象：** 除了 M5 说的快照不跑，`restore()` 也没有任何入口——就算用户想恢复也调不到。
**修法：** 同 M5（接上调用点或工具入口）。

### m13. dataDir 配错了会悄悄建一个空目录往里记

**位置：** `core/src/core.ts:86`（`ensureDir` 无条件创建）。

**现象：** 环境变量写错一个字母，插件不报错，而是在错误位置新建空文件夹开始记——她的真记忆在另一个文件夹里，log 看着是空的，还以为插件坏了。
**修法：** 目录是新建的、且里面没有 `MEMORY.md` 时打一条 `console.warn`（新建空目录本身是合法的，测试环境就是这么用的，所以只告警不报错）。

### m14. 静态 section 注册没防重

**位置：** `dsh-plugin/src/index.ts:266`。

**现象：** 同一进程里插件被应用两次（两个 profile），第二次 `apply` 在 `section()` 上抛 duplicate，整个插件加载失败。需双 profile 实测确认触发条件，修法简单：catch 住 duplicate。
**修法：** 同 B1 第 4 条。

### m15. 触发词出现之前的那几句，永远不进 log（设计如此，但要说清楚）

**位置：** `dsh-plugin/src/index.ts:404-407`（`session/event` 里触发后才开始记）。

**现象：** 一个会话聊了 20 句才第一次说“夏柠柒”，前面 20 句的逐字记录就没了（skill 的 MEMORY.md 摘要可能还留着，但插件的逐字 log 没有）。
**修法：** 不改行为也行，但要在 README 里写明；想修就修 M7（从会话历史里补判定）。

### m16. turn-1 追加的 recall 会永久留在历史里，之后重叠的 recall 会重复注入

**位置：** `dsh-plugin/src/index.ts:341-350`。

**DSH 证据：** `dsh-agent-loop/lib/index.js:906-913`——`preStep` 里是先 `assemble` 再跑 waterfall，所以 turn 1 注册的 context **赶不上**当轮请求，追加是必需的（没有 turn 1 重复注入，我一开始怀疑错了，源码证实了）；但追加的消息会被提交成 user/message 事件、永久进会话历史（Run B live 证实）。

**现象：** turn 2 再问同类问题，fresh recall 和历史里那条 turn-1 追加撞上，同一段记忆出现两次（一次在 history 里，一次在 context 里），浪费 token，也可能让模型以为是两段不同的事。
**修法：** 刷新 context 时先对最近历史去重，或让追加的消息不进持久历史（目前没有这个开关，退而求其次是去重）。

### m17. 两条用户消息赶在 turn 1 之前一起到，只对最后一条做 recall

**位置：** `dsh-plugin/src/index.ts:latestUserText`（`:125`，倒序取最后一条 user 消息）。

**现象：** 第一句的关键词 recall 没跑（第二句的跑了）。影响小，因为两句都在 history 里。
**修法：** 可接受；想修就对 claimed 里的每条 user 消息都跑一遍 recall 再合并。

## 查过、结论是没问题的（每项都有依据）

**1. ctx.on 注册（5 个）：**
- `agent/created`：payload 是 `{agent, source, signal}`，`agent.id` = 会话 id（Run A/B live 证实，和 `agent.session.id` 同一个字符串）。
- `agent/pre-step`：waterfall 入参是 `{messages, turn, step, signal, agent}`，**没有 `sessionId`、没有 `kind`**（Run A/B live 证实）；`messages` 永远是数组（`dsh-agent-loop:902-915`，`claimed` 恒为数组，base decision 也是数组）；每 step 跑一次（turn 循环每轮调 `preStep`），但 step 2+ 的 claimed 通常为空（工具结果走 session history），所以 `turns` 计数不会错；`return next()` 的修法是对的。
- `session/event`：确实是 `(session, event)` 两参，`event.data` 是消息（Run A/B live 证实）；监听器被 DSH 包住，抛错只记 warn、炸不了轮次（`dsh-session:1231-1240`）；rehydrated 的旧事件永不发布，不会重复记录（`dsh-session:1348-1351`）。
- `agent/turn-stopping`：serial、awaited，**只在正常轮次结束时触发**（`dsh-agent-loop:995-1010`；Run A/B 里 error 轮次确实没触发）；抛错会进 turn 的 catch 让轮次失败（见 M6）。
- `ctx.effect`：卸载时跑 final flush，没问题。
- **会话 key 一致性（第 6 项）：pre-step 的 sid（经 `agent.id`）== session/event 的 `subject.id` == agent/created 的 `agent.id`，三处是同一个字符串（Run A/B 里同一个 `session-…` id 全程出现）。没有 key 不一致导致的状态错位；M7 的问题是重置逻辑，不是 key。**

**2. 事件类型：** 一个真实轮次里实际出现的类型都对过：`user/message`（三种形态：真提问带 id、插件追加无 id、`runtime-context` 快照——kind 过滤全都处理对了）、`assistant/message`（嵌套 `data.message`，0.1.2 已修）、`assistant/attempt`（无 content，正确忽略；失败重试时出现多次）、`compaction/start`（存在，handler 会 flush）、`system/message`（`data.message`，按类型忽略）、`request/header`、`request/context`、`session/title`、`step/start`、`step/end`、`turn/start`、`turn/end`、`llm/retry`、`permission/preset`、`sandbox/mode`、`approval/policy`、`agent/inbox/spliced`——全部存在且都被正确忽略。`tool/result`（`createToolResultMessage`）和开发者消息也不会被误记。**漏记的只有 m5/m6/m7 三个内容层面的细节，不是类型层面的。**

**3. systemPrompt：** `section` 返回 void（插件没存它，是对的）；`context` 返回 Cordis effect disposer（函数，插件的 typeof 判断是对的）；旧 context 在刷新时确实 dispose（dispose-then-register 顺序是对的）；问题只在多会话重名（B1）和全局泄漏（M1）。

**4. 工具注册：** `register` 本身不校验 `parameters`（所以裸对象能注册成功，不抛错——这是 M2 能静默发生的直接原因）；`schemas()` 是模型可见的投影（已证实返回裸 map）。`memory_search`/`memory_remember` 的 execute 参数形状和 M4 的门控问题见 M2/M4。

**5. 抛错面：** `session/event` 里抛错被 DSH 兜住（安全）；`pre-step` 和 `turn-stopping` 里抛错会炸轮次（见 M6）；`apply` 里抛错只死插件不死 DSH（见 M3）。`MEMORY.md` 格式不对时解析器是容忍的（返回空层，不抛错）；`log.jsonl` 坏行跳过（不致命）；`index.json` 损坏时重建（`load()` 返回 false 就 rebuild）。**唯一会炸构造函数的是 B2 的毒行——那是 `record()` 写的，不关解析器。**

**7. core 在真实 DSH 条件下：** 单进程内 record 是同步的，无竞态；双进程同目录无文件锁（文档里已写明 single-writer 假设，index 错配的实际影响很小，因为 index 本来就没人查）；空查询返回 0 条（已修好）；快照/恢复见 M5/M9（`restore` 会把 `MEMORY.md` 和日记也 revert 到快照时间——`snapshot.ts:copyDataFiles` 拷贝除 `.snapshots`/`.complete`/`.tmp-*` 之外的**全部**文件，`restoreSnapshot` 会覆盖快照里有的文件；快照里没有的文件才 untouched。安全快照能兜底，但用户不会被告知的）。

**8. mock 测试的缺口（`dsh-plugin/test/mock-test.ts`，30 个 check，core 25/25、shell 24/24 都绿，但盖不住这些）：**
- 假 `systemPrompt.context` 从不抛 duplicate——B1 的多会话冲突完全没练到。
- 假 `ctx.tools.register` 照单全收——M2 的裸 DSL 注册、模型可见 schema 损坏都没练到（mock 里 `loadDefineTool` 同样走 fallback，但假 registry 不校验）。
- 假 pre-step decision 是测试手造的，没有真实的 `{messages, turn, step, signal, agent}` 形状，也没有 `agent.id` 这条 sid 路径。
- 没练多 step 轮次、没练双会话交错（M4 的门控错位）、没练 error 轮次不触发 `turn-stopping`、没练 `apply()` 抛错、没练 `recall()`/`flush()` 抛错。
- 没练 reasoning 块、纯图片消息、中断半截话、token 上限单条巨物、去重误删、单字查询。
- 没练 `endSession`/快照（因为根本没人调，测试也测不到“没跑”这件事）。
- 0.1.2 的回归测试（2-arg 事件、嵌套 assistant）是有的，说明 mock 能接住“形状错了”这类问题，接不住“机制错了”（全局层、link 解析、并发）这类。

**Flush 时机（细节项）：** 最后一条消息是 `session/event` 里同步写盘 + fsync 的，所以**不会丢**；`turn-stopping` 不触发的轮次（error/reject/abort）只影响 `index.json` 的新鲜度，而 index 本来就没人查——实际无害。真正的缺口是快照从不跑（M5）。

**Recall 质量（细节项）：** 大小写不敏感（latin 双向小写）；中文标点会断开跑串（是对的）；近义词/换说法查不到是 keyword-only 的设计上限（不是 bug，但要写进 README）；排序是 keyword 数量主导，recency 只是弱 tie-break。

## 修的优先级建议

1. **先修 B1 + B2**（都是“触发就炸、炸完难恢复”）：context 走 `agent.ctx` + try/catch；`record()`/`tokenize()`/`readAll()` 三层防毒。
2. **再修 M2 + M4**（工具真正可用 + 门控精确）：vendor `defineTool` 或 build 时编译；execute 接 `exec.agent.session.id`。
3. **再修 M5 + M6 + M3 + M7**（快照跑起来、抛错降级、apply 容错、人设标记持久化）。
4. Minor 按 m1（index 死代码）→ m2/m3（去重/上限）→ m5/m6/m7（文本提取）→ 其余的顺序修。
5. mock 测试补：双会话 context 冲突、裸 DSL 注册断言、`agent.id` sid 路径、error 轮次、reasoning/图片/中断、毒记录回归（`record(undefined)` 不得写盘且不得炸构造函数）。
